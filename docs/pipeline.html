Schedule Update Pipeline

How SF Rec & Park pool PDFs become the all_schedules.json the site renders: scraping, PDF extraction with Gemini, health checks, closures, changelogs, and the weekly GitHub Action that ties it together.

At a glance

Everything runs from one npm script, npm run build-schedules, which chains four stages:

Scrape pool pagesscripts/scrape-pool-info.ts → finds each pool's current schedule PDF link
↓
Download PDFsscripts/downloadPdf.ts → data/pdfs/<pool-id>.pdf + data/pdf-manifest.json
↓
Scrape alerts & closuresscripts/scrape-alerts.ts --notify → public/data/alerts.json
↓
Extract, normalize, validate, publishscripts/process-all-pdfs.ts → public/data/all_schedules.json + data/changelog/<date>.json

Alerts are scraped before processing on purpose: an active closure needs to be known when the schedules are assembled so the closed pool's programs can be hidden.

1. Discovering the PDFs

scrape-pool-info.ts starts at the Swimming Pools listing, visits each pool page, and picks the schedule link from the page's Documents row (/DocumentCenter/View/… links). Results go to public/data/discovered_pool_schedules.json.

When a page has only one document, the first link wins. When it has several (e.g. North Beach's warm and cool pool schedules), pickBestPdfLink scores every candidate:

  • + link text mentions "schedule" (+4), "pool", ends in pdf, or matches tokens from the pool's slug
  • +10 / −10 for the requested variant keyword vs. its sibling, so "warm" never resolves to the "cool" PDF
  • − "citywide", "rules", "party", unrelated "mission", or no slug-token match at all

The canonical list of pools (ids, names, addresses, page URLs) lives in data/pools.json.

2. Downloading

downloadPdf.ts fetches each discovered PDF, SHA-256 hashes the bytes, and saves it as data/pdfs/<sanitized-pool-id>.pdf. data/pdf-manifest.json records the URL and hash per pool; if the hash matches, the file is left as-is (only the URL is refreshed if it moved).

3. Alerts and closures

scrape-alerts.ts collects site-wide banners and per-pool notices (both prose on the page and linked notice documents). Anything that mentions a closure is enriched: the notice PDF is downloaded and read by the model together with the alert text to produce a structured Closure (start/end dates, indefinite flag, summary, and suppressPrograms).

  • suppressPrograms is the single gate on hiding a schedule. Partial closures, or ones the model flagged as unsafe to act on, remain alerts only.
  • With --notify, new alerts and new/changed closures trigger Pushover notifications.

4. Processing the PDFs

process-all-pdfs.ts does the real work. For every pool in pools.json with a PDF on disk:

4a. Cache check

It hashes the PDF and compares it with data/extracted/_manifest.json. Unchanged PDFs reuse the cached extract in data/extracted/<pool>.json — no API call. Set REFRESH_EXTRACT=1 to force re-extraction.

4b. Extraction with Gemini

extractScheduleFromPdf (src/lib/pdf-processor.ts) sends the raw PDF to gemini-3.1-flash-lite via the Vercel AI SDK with structured output bound to a Zod schema (PoolScheduleSchema). Settings: temperature: 0 for deterministic reads, maxRetries: 3 for transient failures. The prompt enforces:

  • times as h:mm[a|p] (e.g. 9:00a), Pacific time, full weekday names
  • program names verbatim — normalization happens later
  • stacked programs in one time block split into separate entries, each with its own lane count parsed from "Lap Swim (8)"
  • season name and start/end dates when the PDF states them
  • the expected pool name as a hint, so the model doesn't mislabel the pool

The output is validated again with AllSchedulesSchema.parse before being cached.

4c. Identity and enrichment

  • Pool identity comes from pools.json, not from the PDF text — the PDF can't distinguish pools that share a name (North Beach warm vs. cool). Name matching via pool-mapping.ts is only a fallback.
  • Address, Rec & Park URL, and PDF URL are filled from pools.json and the discovery file.
  • Program taxonomy (program-taxonomy.ts): each program keeps its programNameOriginal, gets a canonical programName, a cleaned display title, and derived tags (activity:*, audience:*, access:*).

4d. Closures

If the pool has an active, program-suppressing closure, it's published with programs: [] and the closure object attached. This also means an empty extract caused by a closure notice isn't mistaken for a broken PDF. A closure that has ended is ignored automatically, so the pool returns the day after reopening.

4e. Health checks and quarantine

Each extract is checked by src/lib/schedule-validation.ts, both on its own and against the previous published data:

CheckSeverity
Unparseable start/end timeerror
End time at or before start timeerror
All previous programs disappeared (baseline ≥ 5)error
Program count fell by more than 50%error
No programs extractedwarning
Schedule covers only one daywarning
Day coverage dropped by 3+ dayswarning

Any error makes the pool unhealthy:

  • Quarantined — previous data exists, so the pool is held at its last known-good schedule.
  • Dropped — no previous data, so nothing is published for it.

Either way the pool's hash is removed from the extract manifest, so the next run re-extracts it. ALLOW_UNHEALTHY=1 bypasses this locally.

Volume of change is deliberately not a health signal. A season rollover changes most programs and is perfectly healthy. Large diffs are reported (with whether the PDFs declared a new season) but never block publishing.

4f. Preservation

Pools that weren't processed this run (e.g. PDF missing) keep their previous entry, unless the pool no longer exists in pools.json — that prevents renamed or split pools from leaving stale entries.

4g. Changelog and output

scripts/changelog.ts diffs the previous all_schedules.json against the new set (added/removed/changed programs, change severity, season change). Anomalies, quarantines, and drops are appended as warnings, and the entry is written to data/changelog/. Then the new public/data/all_schedules.json is written.

Failure policy

The run fails only when nothing usable came out:

  • no schedules at all to publish, or
  • every extracted pool failed health checks (likely a site-wide PDF format change).

One bad PDF never blocks the rest — it sets reviewRequired instead.

5. The weekly GitHub Action

.github/workflows/update-schedules.yml runs every Friday at 20:00 UTC (noon Pacific standard time) and can also be triggered manually.

StepWhat happens
Run pipelinenpm run build-schedules with the Gemini key and Pushover secrets. Marked continue-on-error so the later steps can report.
Check for changesgit diff over public/data/ and data/changelog/.
Commit & pushOnly if changed and the build succeeded: commits as github-actions[bot] with "Update pool schedules YYYY-MM-DD".
Notifyscripts/notify.ts sends a Pushover message: update, no-changes, review-required (only if something was quarantined/dropped), or build-failed.
FailOn pipeline failure, the job exits 1; a separate notify-failure job sends an error notification.

The deployed site picks up the committed JSON on its next build.

Running it locally

Needs GOOGLE_GENERATIVE_AI_API_KEY in .env (Pushover keys optional).

  • npm run build-schedules — full pipeline
  • npm run process-all-pdfs — just re-process PDFs already on disk
  • REFRESH_EXTRACT=1 npm run process-all-pdfs — ignore the extraction cache
  • ALLOW_UNHEALTHY=1 … — publish extracts that fail health checks
  • npm run renormalize-programs — re-apply the program taxonomy without re-extracting
